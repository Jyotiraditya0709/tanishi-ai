# AR3 · red-team report (2026-10-10)

Target: `agent/arena/ar3` at de0075c (`tanishi/arena/frontier_service.py`). Proofs: `tests/arena/test_redteam_ar3.py`.
Every proof is `xfail(strict=True)`: it fails today for the stated reason (checked with `--runxfail`), and turns into an
error once fixed, so the fixer removes the marker. No product code was changed. Existing arena suite: 488 pass.

## Headline

Acceptance 1 ("task text and verifier code never cross the boundary") holds for **the return value of a well-behaved
candidate**. It does not hold against the thing it is meant to stop: the candidate is the agent's own code, and it runs
as the service user, unsandboxed, inside the same process tree that holds the tasks. The exam and the implementer tested
the shape of the output and leaky verifiers; none of them tested a candidate that tries to get a prompt out.
RT-1..4 are one root cause with four exits. The service as built is safe against accidents, not against the agent.

## Breaks

| ID | Sev | Break | Proof test | Smallest fix |
|----|-----|-------|-----------|--------------|
| RT-1 | **high** | `cost` is whatever the executor says (`Attempt.cost`) and is returned verbatim. The executor sees `brief.prompt`, so it encodes the prompt into `cost` (6 bytes per float, exact; one float per task per seed). The prompt crosses the boundary inside an allowed field. Cost is also under-reportable, so a cost-aware gate can be gamed. | `test_cost_cannot_carry_the_prompt_across_the_boundary` | The service measures cost itself (wall time, plus tokens from a metered client) and clamps/quantises what the executor reports; never return an executor-chosen float at full precision. Bounds the channel to a few bits, does not close it. |
| RT-2 | **high** | The executor can write `brief.prompt` to any path the service user can write (world-readable file, the agent's home). Decision 0020 and `ar3-frontier-limits.md` list "side channels", but present them as a candidate that must be adversarial; here it is a 3-line executor. | `test_executor_cannot_write_the_prompt_outside_its_home` | Run the executor stage in a sandbox: no network, writes only to the attempt home (`sandbox-exec`/`bwrap`/landlock, or a third OS user with no write access outside the home). |
| RT-3 | **high** | The executor runs as the store's owner, so it can `listdir`/read the whole store: every task, every verifier path, and the salt. It does not need to guess a path: the store path is a CLI argument the agent chose. Known limit only covers "import the verifier module". | `test_executor_cannot_read_the_store` | Same sandbox as RT-2, plus: only the service process reads the store; the executor child gets the one brief it needs. Run the executor as a *different* user than the store owner. |
| RT-4 | **high** | The CLI does `resolve(args.executor)` in the service process, so any module the agent names runs at import time with the service's privileges, before `evaluate`. The proof patches `json.dumps` and the CLI prints the raw task file. "prints the scores as JSON and nothing else" is false for a hostile module. | `test_cli_output_is_only_scores_even_for_a_hostile_executor_module` | Never import the executor in the service process (AR1 already unpickles it in a child; pass the dotted name, not the function). Build the output from validated fields only (`task_id_hash` hex, finite floats). |
| RT-5 | medium | No query budget. Scores are an oracle: with `contains`-style or exact verifiers a candidate that echoes a guess set recovers a hidden needle in log2(n) calls (3 calls for 8 words; 20 for a million-word dictionary). Known limit says only "learns which task is hard". | `test_a_hidden_needle_cannot_be_bisected_out_of_the_scores` | Per-store/per-candidate query budget, logged outside the agent's reach; Frontier verifiers must not return graded partial credit on enumerable answers. Cannot be closed by code alone: it is also a task-design rule. |
| RT-6 | medium | `.salt` is created with `O_EXCL` then written in a second step. A crash (or a second process reading in between) leaves a 0-byte salt; every later call raises "salt is too short; delete it" until a human deletes it. Concurrent first calls can hit the same window. | `test_a_salt_left_empty_by_a_crash_does_not_brick_the_store` | Write the key to a temp file in the store, `fsync`, then `os.link` it to `.salt` (atomic, fails if it exists). |
| RT-7 | medium | `evaluate()` swaps `os.environ[TANISHI_CORE_STATE_DB]` and restores a *saved* value. Two overlapping calls in one process: B saves A's temp path, A restores and deletes it, B then "restores" the deleted path. The caller's Core State path is now dead for the life of the process. Known limit says other threads "see the throwaway db"; the permanent corruption is worse and not listed. | `test_overlapping_evaluations_restore_the_callers_db_path` | Hold a module-level `threading.Lock` for the whole swap (smallest), or give `run()` an explicit `db_path` argument and stop touching `os.environ`. |
| RT-8 | medium | `seeds` has no upper bound. `evaluate(c, seeds=10**6)` starts 2×10^6 serial subprocesses with up to 3600 s timeouts each, and AR1 `run()` holds every row in memory. One call from the agent pins the service user. | `test_seeds_are_capped` | Cap seeds (e.g. 10) and tasks×seeds×timeout in `evaluate`, raise `ValueError` before any attempt. |
| RT-9 | medium | `cost` is the sum over seeds of finite floats and can overflow to `inf` (`1.7e308` × 2). `json.dumps` then prints `Infinity`, which is not JSON; a strict parser (or a SQL budget check, `inf > x`) misbehaves. | `test_cost_stays_finite_and_json_valid` | Clamp each cost and the sum (fixed with RT-1), and `json.dumps(..., allow_nan=False)` in the CLI. |
| RT-10 | medium | A task whose verifier cannot be imported (typo, moved module, missing dependency) scores 0 and is returned like any failed candidate. A broken Frontier store looks like a terrible candidate; a regression gate rejects good work, and the service gives no way to tell. | `test_a_task_with_a_missing_verifier_is_refused_not_scored_zero` | Preflight in `evaluate`: `resolve()` every task's verifier in the service process and refuse the store (message without names) if any fails. Do not map attempt-time failure kinds to errors: a candidate can induce those and it would add an oracle. |
| RT-11 | low | Only top-level `*.yaml` files are loaded and checked. `t2.yml`, `T2.YAML`, or tasks in a subdirectory are silently skipped, so the score covers fewer tasks than intended, with no signal. The service's own docstring says a silently skipped task changes what the score means. | `test_a_task_file_with_another_extension_is_refused_not_skipped` | Refuse any directory entry other than `*.yaml` and `.salt`. |

## Found, no test (judgment, conflict with the exam, or not deterministic)

- **Empty store returns `[]`.** `evaluate` on a directory with no tasks returns an empty list, so a gate written as
  `all(e["score"] >= x for e in out)` passes for a mis-pointed store. The AR3 exam asserts this behaviour
  (`test_empty_store_returns_no_scores_and_no_fake_ones`), so I did not write a proof. Callers must check `len(out) > 0`;
  consider an `expected_tasks` argument or a distinct exception. Human decision.
- **Ancestors are not checked.** Owner/mode checks cover the store, its task files and the salt, not its parents. If the
  agent owns a parent directory it can rename the store away and swap in its own between the check and the read (it
  fails the owner check, so this is an availability problem, plus a check-then-use window). Check `lstat` of each parent.
- **Temp leftovers.** A `SIGKILL` or power loss mid-run leaves `tanishi-frontier-*` (db with raw task ids and verifier
  reasons) and `tanishi-arena-*` dirs in `$TMPDIR` forever. 0700, but the reasons are exactly what the service tries to
  keep from the caller. Sweep stale `tanishi-frontier-*` dirs older than a day at start, or put them under the store.
- **Cost is lost on failure** (AR1 limit, still true): a timed-out executor that burned money reports cost 0.
- **Serial, two interpreters per attempt** (AR1 limit): 100 tasks × 3 seeds is ~1.5–2 minutes of overhead.
- **Deployment is untestable from here.** Nothing in the repo creates the second OS user or the sudo rule; acceptance 2
  ("a path the agent OS user cannot read") is met only on paper until a human does that. RT-2/3/4 mean even that is
  not enough: a second user for the *service* does not help while the executor is the same user.

## What I tried and found sound

Boundary shape: exactly three keys, plain floats, sorted by hash; no ids, prompts, reasons, exception text or candidate
output in the return value, in errors (no `__cause__`/`__context__`), on stdout/stderr or in caplog. Hash: HMAC with a
random per-store key, not a bare digest; differs between stores; not confirmable by guessing ids. `.salt` created 0600 with
`O_NOFOLLOW`; open salt, symlinked task file, group/world-readable dir or file, store inside the checkout, missing store,
duplicate ids, invalid YAML, duplicate YAML keys and non-string candidates/seeds are all refused with messages that quote
nothing. Verifier raising / NaN / out-of-range scores 0 (AR1). Caller's env is restored on a single call, including on
error. The throwaway db is deleted and holds nothing the caller can see. Nothing was written to the working tree or home.
No secret, personal text or db file was added by this review.
