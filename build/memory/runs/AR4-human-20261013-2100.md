# AR4 · Sealed Vault, first build (human node, built with Claude) · 2026-10-13

**What landed.** `tanishi/arena/sealed.py` (client and vault side), `tanishi/arena/canary_scan.py` (standalone, root
runs it nightly), `scripts/vault/` (setup, wrapper, G0 check), 42 tests, decision 0029. Separately and privately: 36
sealed tasks with their checks and canaries, delivered as an encrypted bundle that is decrypted only into the vault
user's home. Every check was run against a right and a wrong answer (72 of 72 as expected; code in a Landlock sandbox,
tools through the real registry and event log; the random-fixture tasks three more times, all as expected).

1. **What did we learn?** The Frontier service (AR3) already was most of a vault: private store, salted hashes, a
   child that sends back only numbers. The vault adds a second OS user, one sudo door, one read per candidate,
   receipts, canaries and a root-run scan with a leak lock.
2. **What failed, and why?** A selftest run from outside an editable dev install scored 0 everywhere: AR1's sandbox
   grants `sys.path` entries only, and an editable install puts `tanishi` behind a finder, not on `sys.path`. The
   vault installs non-editable. A `Dog's name` label broke a single-quoted `printf` in a task setup; caught by the check
   run, label changed.
3. **Which assumption was wrong?** That the vault could run a real candidate the way Frontier runs an executor. It
   cannot yet: the executor stage cannot read the candidate's copy, and the vault user has no isolating backend on
   macOS. Written up for the human: `open-problems/AR4-candidate-access.md`.
4. **What should the next agent know?** Never put a whole canary in a file of this repo (a test fails). Gates that use
   sealed scores must treat `SealedRefused` and `SealedUnavailable` as no pass, and must not call `.mean` on an empty
   result. IL1 should build `tanishi/arena/answer.py` (`answer(request) -> str`): both IL1 and the vault need it.
