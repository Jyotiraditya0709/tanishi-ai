# L1 red team: Learning Compiler passes 1, 3, 4 (2026-10-11)

Branch `agent/compiler/l1`, commit before this one: `2a6b9aa`. Proofs: `tests/compiler/test_compiler_redteam.py`
(25 tests, **24 fail today**, each failure is a break below; the one that passes is R10, kept as a guard).
The exam and implementer suites (68 tests) pass unchanged; I changed no source and no existing test.

Severity: High = wrong learning or a secret/personal text escapes; Medium = the landing law or an invariant can be
bypassed or lost; Low = silent loss of a lesson or a hardening gap.

## Breaks

### R1 · High · the prediction is self-reported, and the ledger row is never read
`compile_experience` scores surprise from `exp.prediction` (what the caller typed), not from the CS5 row the id names.
- Ledger holds "success at 0.95"; the Experience says "expected failure at 0.95"; the task fails. Surprise lands as
  0.0025, the ledger says 0.9025. Hindsight predictions are indistinguishable from real ones.
- An id that is not in the ledger only logs a warning, and the experience still lands full gain (`pred_never_written`
  at 0.99 gives gain 0.98). Gain is the thing OBS3 will rank on.
- An id that names an unrelated row (e.g. a `tool:calc` prediction) is resolved with the *task's* `{"success": ...}`,
  so the tool's own result and latency can never be written to its row (`AlreadyResolvedError` for the registry).
Tests: `test_R1_*` (3). **Fix:** read the row (`predictions` has the row; add a `get`), refuse unless `expected` and
`confidence` equal the Experience's, `about` starts with `task:`, and the row is unresolved or resolved by this
compiler; an unknown id lands nothing with gain (or gain 0).

### R2 · Medium · attempt identity is the prediction id alone
`find_recorded` matches only `payload.prediction.id`, in any event of kind `experience`, from any actor.
- A retry loop that predicts once and compiles each attempt records only the first; the second attempt is lost and its
  belief cites the first attempt's event (a belief about tool `beta` whose evidence event has no `beta` action).
- An event of kind `experience` from another actor (`intruder`) is adopted as the record.
Tests: `test_R2_*` (3). **Fix:** match `actor == ACTOR` and compare a digest of the whole record (task, actions,
verifier_result); if the id matches but the digest does not, refuse (or record and link both).

### R3 · High · secrets and input text in beliefs, candidates and the log
1. `_pass4_run` builds `output` with `str(a["output"])` and never redacts: a failed output `Bearer sk-ant-...` is in the
   candidate's code (`FAILED_OUTPUT`) and test, returned in `Emission.payload`, which a caller stores as a skill.
2. The generated test embeds `json.dumps(tool_input)` (`input_json`). Decision 0026 item 10 and the code docstring say
   inputs are digest-only; the test source holds them in full, and `compiler_emit` writes that test to the log (up to
   4000 chars, only secret-shaped text redacted). Personal tool input lands in the log and in git with the skill.
3. `_signature` dumps a dict output to JSON and then regex-redacts the text, so a secret under a secret-named key
   with a list or dict value leaks: `{"token": ["abc..", "def.."]}` becomes `{"token": [REDACTED]"abc..", ...}` and
   `{"credentials": {"user": "alice", "pw": "hunter2"}}` keeps `alice` and `hunter2`. These go into a CS3 belief object.
Tests: `test_R3_*` (4). **Fix:** `events.redact(value)` (structural) *before* `json.dumps` in `_signature`; redact `output`
in pass 4; in the test, replace `input_json` with the digest (`seen_failing` already matches by digest: compute
the expected call from `input_digest` constants, or test with a sentinel input that hashes to it).

### R4 · Medium · the item that is checked is not the item that is stored
The check runs on the raw item. `emit()` then redacts and clips strings to 4000 chars. A tool name of 3000 chars makes
the candidate's code over 4000, the check passes, `landed=True`, and the logged code is `...[N more chars]`: it does
not parse. The same holds for any redaction hit (R3). A landed skill candidate lives only in the event log, so the
stored artifact never passed its own test. Test: `test_R4_*`. **Fix:** in `_land`, compute `stored = events.redact`
(with the clip) of the item and run `check` on `stored`, or refuse an item that the log would change; cap the tool
name length in `Experience`.

### R5 · Medium · `run_skill_test` can be faked by the code or the test
All three are one-liners; none needs the candidate to be hostile model text, only text a later pass produces.
1. Code does `import __main__; print(__main__.src["marker"] + " 3"); os._exit(0)`: the marker is a global of the driver
   (`src`), so it is not secret. Known-limits listed "reads the marker from stdin"; stdin is consumed, `__main__` is not.
2. The test file may redefine the function under test and then test its own copy (`def f(): return 2` + `assert f()==2`).
3. `test_*` callables are collected from the shared namespace, so the *code* can supply its own `test_*` and the "test"
   can be `X = 1`: "code plus a test" is satisfied with no test.
Tests: `test_R5_*` (3). **Fix:** AST-collect top-level names; refuse a test that defines a name the code defines (2) and
count only `test_*` defined by the test source (3). For (1) there is no in-process fix: run the driver's verdict from a
fd the code cannot name, or accept it is not a defence and say so until SEC1's sandbox lands; do not describe the marker
as stopping forgery.

### R6 · Medium · a recovered transient failure becomes a guard against a call that worked
Actions: `fetch{id:7}` fails (timeout), `fetch{id:7}` succeeds, `answer` is wrong. Pass 1 names step 0 decisive; pass 4's
guard flags input `{id:7}` for `fetch`, the exact call that succeeded on retry. A wrong skill, and "decisive step" blames a
step the agent recovered from. Tests: `test_R6_*` (2). **Fix:** a failed action whose tool and input digest
later succeeded is *recovered*: skip it for decisive step and pass 4; pass 3 may keep it at lower confidence.

### R7 · Medium · an Experience is frozen only at the top level
`frozen=True` stops `exp.verifier_result = ...`, not `exp.verifier_result["passed"] = True`, and the constructor keeps the
caller's own dicts. A verdict flipped between `record()` and `compile_experience()` makes the log say "failed" and the
compiler learn from "passed" (or the reverse). Validation also runs only at construction. Tests: `test_R7_*` (2).
**Fix:** `copy.deepcopy` the fields in `__post_init__` (via `object.__setattr__`), and have `compile_experience` rebuild
`Experience.from_dict(exp.to_dict())` so a later mutation cannot reach it.

### R8 · Medium · check-then-act on the record, and re-compile is not idempotent
- Two threads compiling one attempt both see "no record", both record: two `experience` events, two beliefs.
- Compiling the same Experience twice lands every belief twice (known-limits listed this; it is a duplicate row per call
  and CS3 stores identical triples as separate rows). Pass 3's evidence count is therefore not evidence.
Tests: `test_R8_*` (2). **Fix:** make record-or-find one transaction (an index/unique key on prediction id, as the
known-limit already suggests), and write a `compiler_done` marker keyed by experience event id + pass version; skip
passes that already landed (or look up `belief` by `source` + evidence event before adding).

### R9 · Low · shapes that cost the lesson
- Mixed-type dict keys in a tool output (`{1: "a", "b": 2}`) pass the constructor (`json.dumps` without `sort_keys`) and
  then kill pass 3 and pass 4 (`sort_keys=True` raises) for exactly the failure that mattered: `compiler_pass_failed`.
  **Fix:** validate with `sort_keys=True`.
- A context nested 5000 deep raises `RecursionError` from the constructor, not `ValueError`. **Fix:** catch it.
- A failed action with no `input` key (common for no-argument tools) yields a candidate that is refused ("test failed"):
  `seen_failing(tool, None)` skips the digest branch but the generated test calls it with `null` and expects True.
  **Fix:** treat a missing input as `{}` in both the digest and the test.
- A retry storm (200 identical failures in one experience) lands 200 identical beliefs and 200 emit events from one
  observation. **Fix:** dedupe by `(tool, signature)` per experience and put the count in the evidence.
Tests: `test_R9_*` (4).

### R10 · Low (perf) · `find_recorded` decodes every experience: not a break yet
1,500 experience events of ~6 KB each: still under 50 ms, so the test passes. It is linear (known-limits already says
so) and runs once per compile, so at the swarm's volume it will become the slowest line of the compiler around a few
tens of thousands of experiences. Fix with R2/R8's index; no urgency.

## Tried, found sound
- Malformed fields, NaN/inf, bool-as-number, blank names, unknown keys: refused as the constructor claims.
- Hash chain after a mix of landed, refused and raising passes: `verify_chain` stays valid; no mid-write fork seen.
- A raising `run`, raising `check`, non-tuple verdict, bool/NaN/str gain, huge gain: each is a logged refusal.
- Code injection through tool name or output into the generated skill source: `repr()` quoting held (`"`, `'`, newlines,
  `{}` and format braces in values).
- Pass 4 timeout: `subprocess.run` kills the child and returns; an infinite loop cannot hang the compiler.
- Frontier/sealed material: the compiler never reads `vault/`, `builder_vault/` or Frontier tasks. One concern, not a
  break: `verifier_result.reason` and `outcome` are written whole into the agent-readable event log; the Arena must
  hand the compiler a reason that is safe for the agent to see (Frontier verifier reasons carry raw task ids and details,
  see `known-bugs/ar3-frontier-limits.md`).
