## The four questions

1. **What did we learn?** Once the human had decided, both fixes took one line each. All the work in the previous
   two rounds went into moving the exam, not the code. When a red-team proof and an exam test give opposite
   answers for the same sequence, ask for a ruling straight away.
2. **What failed, and why?** Nothing failed. One of my own tests (`test_clustering_eval`) used the creation
   shortcut that A13 removes. It was already flagged in the repair-2 notes, so the rewrite was expected.
3. **Which assumption was wrong?** That `set_predicted_rate` had to go. The exam only needs it to be untrusted, so
   keeping it as a what-if that never counts breaks no caller.
4. **What should the next agent know?** `mastered` now implies `forecast_trusted`. To make a node mastered, write
   the CS5 prediction (`about = "capability:<id>"`) before the first `record_outcome`, then pass its id to
   `forecast_from_ledger`. A node scored before its forecast can never be mastered. Loosening that needs
   per-outcome history (known-bugs `e3-capability-graph-limits.md`).
