# CS4 · tester run

1. **What did we learn?** The goals acceptance can be tested through `add_goal`, `active_goals` and the default Core State db (`TANISHI_CORE_STATE_DB`, which `tests/conftest.py` points at a temp path). The "tanishi never above an active user goal" property reduces to: the owner column of `active_goals()` is `user*` then `tanishi*`, whatever the ranks, parents or statuses.
2. **What failed, and why?** Nothing ran against an implementation. The exam fails now with `ModuleNotFoundError: tanishi.core_state.goals`.
3. **Which assumption was wrong?** None known yet. Assumptions the spec does not state:
   - `add_goal` / `active_goals` take no connection and use `open_db()` (and migrate) on the default path.
   - A new goal has `status = 'active'`; any other status value (tests use `done`, `dropped`) is excluded from `active_goals()`.
   - `Goal` has attributes `id, title, owner, parent_id, rank`.
   - Invalid owner raises `ValueError`; unknown parent raises `ValueError`, `KeyError` or `sqlite3.Error`.
   - "Then by rank" has no stated direction. Tests accept ascending or descending, but require the same direction for both owners.
4. **What should the next agent know?**
   - **Spec gap:** the interface has no way to re-parent a goal, and `add_goal` mints a fresh id, so a cycle cannot be made through it. The cycle tests therefore run raw `UPDATE goals SET parent_id = ...` on a second connection and expect `sqlite3.Error`. The implementer will need a new migration (`0002_*.sql`) with triggers that reject self-parent and cycles (0001 is frozen, decision 0007). If you would rather add a `set_parent()` function, the human has to amend the spec and these tests.
   - Property tests use seeded `random`, not Hypothesis.
