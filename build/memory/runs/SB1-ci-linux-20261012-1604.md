# SB1 · CI-Linux repair (2026-10-12), implementation agent

Branch `agent/hardening/sb1`. The PR's CI run (ubuntu-latest, Python 3.12, Landlock + seccomp backend) gave
3 failed, 2510 passed, 10 skipped, 7 xfailed. All three failures were in SB1's own `tests/sandbox/test_sandbox_impl.py`.
In each one the sandbox did its job and the probe crashed before it could print a report.

## Reproducing on Linux: not done here

Every `docker run` was refused by this session's permission mode. It was non-interactive, so nobody could approve it.
I never saw the Linux backend run. The root causes below come from the CI log and from reading `_launch.py`. CI is the
final judge of the fix.

## Root causes

1. **`test_untrusted_candidate_cannot_find_another_processes_environment`.** The probe did
   `for pid in os.listdir("/proc") if os.path.isdir("/proc") else []`. `isdir` is a stat, and Landlock allows it.
   `listdir` needs READ_DIR on `/proc`, and no rule grants that (backends.py grants only a few machine-fact files
   under `/proc`, plus the launcher's own `/proc/<pid>`). So it raised `PermissionError: [Errno 13] '/proc'` outside
   any `try`. stdout was empty, and `assert "DONE" in res.stdout` failed.
2. **`test_docker_sock_and_ssh_agent_stay_unreachable[True|False]`.** The task card guessed that the filter killed
   the process. **It does not.** `_launch.py:98` sets `_SECCOMP_EPERM = 0x00050000 | 1`, which is
   `SECCOMP_RET_ERRNO | EPERM`, and every refused call goes there. The real cause was that the probe called
   `s = socket.socket(socket.AF_UNIX)` *above* its `try`. The filter refuses `socket(AF_UNIX)` itself, not
   `connect()`. So the first iteration raised an uncaught `PermissionError`, nothing was printed, and `json.loads("")`
   failed with `JSONDecodeError`. On macOS, sandbox-exec allows `socket()` and refuses `connect()` inside the `try`,
   which is why it passed there.

## What changed

- `tests/sandbox/test_sandbox_impl.py` only. No Landlock or seccomp rule was touched. The exam and the red-team file
  are unchanged.
  - The env probe (`_FIND_ENV`) wraps every read and listing. Each `OSError` adds 1 to `blocked`, and the probe
    always prints `{"found", "blocked", "control"}`. It also tries the holder's pid directly, so a refused listing
    cannot make the search vacuous. If ctypes cannot be loaded for the macOS sysctl loop, that also counts as
    blocked. Controls: (a) the same probe run unconfined must report `found: true`; (b) inside the sandbox, the
    probe must read a `control.txt` the test planted in its workdir (`control: true`).
  - The socket probe runs each attempt in a forked child that reports through a pipe. Any exception is
    `BLOCKED <type>`, a signal is `KILLED signal N`, and a child that reports nothing is `BLOCKED no report`. The
    parent always prints the full JSON. Only `GOT ...` counts as reached. Controls: (a) the same probe run
    unconfined must get the planted token; (b) a `socketpair` target inside the sandbox must return `GOT PAIR`, which
    proves that the fork/pipe machinery works under confinement. (b) replaces the old in-test `connect` control.
- Decision 0025 §5 now records that the filter returns EPERM (it does not kill), and the reason: the candidate gets a
  clean error and harnesses keep running. Probes must wrap the call that creates the socket.

## The four questions

1. **What did we learn?** A probe that proves "blocked" has to survive being blocked. On Linux the block comes
   earlier than on macOS: at `socket()` rather than `connect()`, and at `listdir("/proc")` rather than the per-pid
   open.
2. **What failed, and why?** The probes were written and run only on macOS, where sandbox-exec refuses later, at
   calls that were inside the `try`.
3. **Which assumption was wrong?** That seccomp kills. It returns EPERM. The fork-per-attempt wrapper is there
   anyway, so the test also holds up if someone changes the action to KILL.
4. **What should the next agent know?** Docker cannot be launched from a non-interactive session with this
   permission mode, so plan Linux checks for CI or for an interactive session. The socket test's control is now
   `socketpair` inside the sandbox plus an unconfined run, so do not drop either one.
