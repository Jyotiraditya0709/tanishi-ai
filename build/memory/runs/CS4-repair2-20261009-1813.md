1. **What did we learn?**
   - The stale-ancestor bug for `INSERT OR REPLACE` was real. A leaf re-inserted under another parent, or as a root,
     kept its old ancestor rows next to the new ones. A REPLACE under the same parent hid the bug, because the rows
     were the same.
   - The fix belongs at the end of the BEFORE INSERT trigger. BEFORE triggers run before REPLACE deletes the old row,
     and every RAISE has already passed by then. A refused statement rolls back the DELETE along with everything else,
     so a refused REPLACE (for example red-team G6, a smuggled cycle) keeps the old rows.
   - The owner check is one line (`NEW.owner IS NULL OR NEW.owner NOT IN (...)`). The `IS NULL` part is needed,
     because `NULL NOT IN (...)` is NULL, and a NULL condition would let the insert through.
2. **What failed, and why?** Nothing in the code. My first version of the new test expected 3 + n rows in
   `goal_ancestors` and should have expected 4 + n: I forgot the (b, a) row. The two real failures (stale rows) showed
   up in the same run, so the bug was confirmed before the fix.
3. **Which assumption was wrong?** The known-bugs entry said the stale rows only made the checks stricter. That holds
   for the cycle and depth checks, but the rows were also simply wrong data in `goal_ancestors`. Anything that reads
   the table to list a goal's ancestors would have been wrong.

   - `goals_check_insert` now does three jobs: it refuses bad inserts, refuses an owner change through REPLACE, and
