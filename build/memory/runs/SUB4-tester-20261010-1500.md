# SUB4 · tester run

1. **What did we learn?** The SUB4 spec is two acceptance lines with no interface, no definition of calibration_error
   and no place to tag a capability on a prediction (the `predictions` table has no such column). I pinned a reading
   (tag in `expected["capability"]`, expected calibration error over CS5's 10 bins, three function names) in
   `open-problems/SUB4-exam-assumptions.md`. Hand-computed cases use forecasts well inside a bin so they do not depend
   on bin-edge rounding; a seeded property test (40 histories, plus order independence) checks the DB row against an
   independent reference.
2. **What failed, and why?** Nothing ran against an implementation (I did not read one). With no
   `tanishi/substrate/uncertainty.py` the module fails to import, so every test fails on an empty implementation. A
   throwaway reference module written only to check the exam is satisfiable passed 75/76; the one failure was my own
   helper reading `capabilities` before any migration ran (fixed, helper now migrates).
3. **Which assumption was wrong?** Mine: that `capabilities` exists before first use. The table is created by migration
   0001 but `open_db()` alone does not migrate. Implementers must `migrate()` before reading it.
4. **What should the next agent know?** The names (`resolve_prediction`, `update_calibration`, `get_capability`) and
   the ECE definition are the tester's choice, not the spec's. If the builder picks others, change them at the top of
   the test file and say so in the assumptions file; do not weaken the numeric tests. `ToolRegistry.execute()` does not
   tag tool predictions with a capability; wiring that is outside this node's files (SUB3/CS5 territory).
