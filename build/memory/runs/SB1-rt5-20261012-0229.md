## What changed

- `test_rt5_candidate_cannot_read_the_arguments_or_environment_of_another_process_of_the_user` (no xfail, runs on
  Linux too): a helper process holds the token only in its environment (its argv is a fixed string). The sandbox is
  `Sandbox(trusted=False, ...)` with the default backend; `SandboxUnavailable` makes the test skip with a reason. The
  token reaches the candidate on stdin, so it is on no command line and in no candidate environment. The candidate
  scans `/proc/*/environ|cmdline`, sysctl KERN_PROCARGS2 (macOS), and `ps -E` / `ps eww` / `ps auxeww` listings.
- Two controls make a silent pass impossible: an unconfined `ps -E` must see the helper's token (macOS), and the
  candidate starts a child with its own control value in its environment and must find it in its scan.
- `test_rt5b_candidate_can_read_its_own_arguments_which_is_not_a_sandbox_break`: the old attack as a plain passing
  test, with the reason in its docstring.
- Conflict R1 marked resolved; known-bugs file updated.

## The four questions

**What did we learn?** Through the real candidate path (Docker) every route comes back empty, and the control child
is visible, so the scan works. The container has its own pid namespace, so the host helper is invisible there.

**What failed, and why?** Nothing failed. My first splice attempts were blocked by the command checker (heredocs and
`python script.py` need approval here); `Edit` on the test file worked.

**Which assumption was wrong?** The red team's rt5 assumed a token in the candidate's `-c` program could show a
sandbox leak. A process always reads its own argv, so the test proved nothing about isolation.

**What should the next agent know?** Put secrets on stdin or in a file, never in argv, when writing a test or a
caller for untrusted code. R2 (AR1's executor stage on sandbox-exec, `trusted=True`) is still open and is not
covered by rt5.
