# CS1 · tester run

1. **What did we learn?** The acceptance lines can be tested through `open_db` and `migrate` alone, so the exam needs no knowledge of where migrations live. To force a failed migration I use `sqlite3`'s `set_authorizer` to deny `CREATE TABLE` or the `schema_version` insert. That gives a mid-migration failure on any implementation.
2. **What failed, and why?** Nothing ran against an implementation. By design the exam fails now with `ModuleNotFoundError: tanishi.core_state`, because the package doesn't exist yet. Ruff's blind `Exception` rule (B017) pushed me to assert `sqlite3.Error` on a failed migration. An implementation that wraps the error in its own exception type would fail those tests; the spec doesn't say either way.
3. **Which assumption was wrong?** None known yet. Assumptions I made, which the spec doesn't state:
   - `open_db()` creates `~/.tanishi/` when it is missing.
   - The `PRAGMA journal_mode=wal` setting persists in the file.
   - The `events` table has an auto-assigned integer id.
   - `schema_version.applied_at` is non-empty.
   - Foreign-key columns (`evidence.belief_id`, `goals.parent_id` and so on) are unconstrained or nullable; the round-trip test writes NULL there.
4. **What should the next agent know?**
   - Property tests use seeded `random`, not Hypothesis, which isn't a declared dependency.
   - The legacy-db check uses sentinel files plus a spy on `sqlite3.connect`. It misses an implementation that did `from sqlite3 import connect` before the spy; the byte-hash check on the sentinel files still catches writes.
   - Hash-chain behaviour for `events` is out of scope for CS1, so only the schema is tested.
