## Design notes (no test; for the owners of later nodes)

- **Evaluation leakage.** `open_db()` hands out a raw read-write connection to everything, including `experiments.score`
  and `capabilities.ability`. Any code that holds it, including a candidate under test, can rewrite its own results.
  The DAL (CS2 and onward) needs a read-only open mode and a single writer path for `experiments` and `capabilities`.
  CS1 alone cannot be blamed, but a "thin data-access layer that every node writes through" is not there yet.
- **Secrets in an append-only log.** Once R9 is fixed, `events.payload` can never be redacted: the hash covers it.
  If a secret or personal text ever lands in a payload, the only cure is rebuilding the chain. The event writer must scrub
  before hashing (CLAUDE.md: no secrets or personal text in events), and the hash should cover a redactable-by-design shape
  (hash of payload fields, not the raw text) if that is ever wanted. Decide before the first writer is built.
- `migrate()` itself holds up for ordinary use (see below); the weak points are the file-handling edges and the schema.

## What I tried that held

- Two processes migrating one fresh file at once: one applies, the other sees the version row. No double apply.
- A migration failing on its last statement: whole migration rolled back, no `schema_version` row.
- Database newer than the code: refused. Connection with an open transaction: refused.
- `;` inside `--` comments, `/* */` comments, string literals and trigger bodies: splitter is correct (4 new passing tests).
- A file that is not a database, a zero-byte file, and `""` as the path: error raised, connection closed, nothing leaked.
- Legacy names (`tanishi.db`, `db.sqlite`, `finance.db`, upper-case variants): refused. Only the symlink route (R7) gets round it.
- WAL on, foreign-keys pragma on after `open_db`.

Not tried: kill -9 mid-migration with a real subprocess (SQLite's own journal covers it; I did not prove it here), network
filesystems, and a read-only filesystem.

## Verdict

CS1 meets its written acceptance list. It should not be treated as safe ground for T0 nodes to build on until
R9, R10 and R6 are fixed, because they sit under the hash-chain and personal-data promises every later node assumes.
R7 and R3 contradict two of the four acceptance lines under adversarial input. Suggested fix packaging: one `0002_integrity.sql`
(R9 to R16, a single table rebuild pass), plus small edits to `db.py` (R1 to R8).
