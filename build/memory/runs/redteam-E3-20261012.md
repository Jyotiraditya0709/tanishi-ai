## Noted, no proof

- **Candidate churn.** `candidate_id` hashes the cluster's texts, so a cluster that gains one text variant tomorrow gets
  a new node and the old one stays (already listed in `e3-capability-graph-limits.md`). With RT-4's fix, link by
  overlap with an existing candidate's instances instead of by hash.
- **Seeds do not update.** `seed()` leaves existing nodes alone, so when AR4 replaces Practice ids with sealed ones, an
  existing db keeps the old instances. The AR4 swap needs a migration step (or `seed(replace_instances=True)`).
- **Confidence is a function of n only** (`n / (n + 10)`); it does not shrink for a noisy node. Fine for now, but it is
  not "her confidence" in any sense the router could weigh against SUB4's calibration.
- **Known limits re-confirmed:** self-reported outcomes, Practice ids are not sealed, CLI steps carry no family (so
  RT-8 applies to one big family).

## What I tried that held

- Duplicate/blank/control-character/oversized ids, bool and NaN/inf rates, 0.9 and 0.10 float boundaries: all rejected
  or inside tolerance as specified.
- `requires` cycles of length 2 and 3, self edges, `fails_together` stored once regardless of direction.
- Re-recording an outcome never double-counts (primary key + upsert); outcomes for ids outside `instances` are ignored
  in the tally; `refresh` is idempotent.
- Concurrent `nightly` runs: `BEGIN IMMEDIATE` plus the `candidate_id` clause gave one node, no crash.
- Input order and shuffled trace order do not change clusters; `candidate_id` is printable whatever the text held.
- No step text, prompt or error message is persisted: only the hash id, the family string and counts reach the db.
  (`error` in OBS1 is the exception type only, decision 0023 rule 2.)

## After-task questions

1. **What did we learn?** The graph's rules are solid on the values they are given and weak on what they are not
   given: coverage (RT-1), time (RT-3) and text content (RT-5, RT-6). The nightly run trusts that a span with an error
   is a failed task, which the trace format does not say.
2. **What failed, and why?** The suite checked the 0.9 and 0.10 boundaries precisely but always with every instance
   scored and a forecast set first, so partial coverage and ordering were never exercised.
3. **Which assumption was wrong?** "n = instances with an outcome" as the denominator of a mastery claim. A rate over
   the instances you happened to run is not a rate over the sealed set.
4. **What should the next agent know?** Fix RT-1, RT-2, RT-6, RT-7 first (small, local, change what lands in the
   graph). RT-3 needs a human decision on where forecasts live. Do not wire `mastered` into any promotion gate until
   RT-1 and RT-3 are fixed and outcomes come from verifier-scored Arena rows.
