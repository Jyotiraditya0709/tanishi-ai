# CS5 · implementer run (2026-10-09)

1. **What did we learn?** The `predictions` table from 0001 was enough, so no migration. A base-rate forecaster with
   Laplace smoothing (prior 0.5) scores a run of failures exactly like a run of successes, so the exam's
   "failures score worse" test could not pass with it. A prior that tools usually work (0.75, weight 4) fixes that and
   is honest. Evaluation (`test_predictions_impl.py::test_eval_*`): on simulated tools at 95% and 20% success the
   learned forecast beats a 0.5 coin by more than 0.05 Brier within 60 calls, and is never worse than the coin or the
   fixed prior by more than 0.02.
2. **What failed, and why?** Five CS2 tests now fail: they assert a tool call writes only `tool_call` and
   `tool_result`, and the CS5 exam requires a `prediction` event before `tool_call`. See
   `open-problems/CS5-exam-conflicts.md`. My first eval asserted "beats a coin" at a 60% success rate too; the best
   possible Brier there is 0.24 against 0.25, so it failed on noise. Restated with a margin.
3. **Which assumption was wrong?** That adding events to `execute()` was additive. Tests that compare the whole log to
   an exact list make every new event kind a breaking change.
4. **What should the next agent know?** Read decision 0014. Keep `unresolved_older_than` the only public name in
   `predictions.py` containing unresolved/stale/overdue (the exam finds the helper by name). When you test the event
   log, filter by the kinds you check, never compare the whole log to an exact list.
