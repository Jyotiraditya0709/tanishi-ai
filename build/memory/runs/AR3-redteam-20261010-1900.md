# AR3 · red-team run, 2026-10-10 19:00

1. **What did we learn?** The AR3 boundary is only as strong as the executor's isolation. The return value is clean, but
   the candidate is the agent's own code running as the service user: it can encode the prompt in `cost`, write it to a
   world-readable file, read the whole store, or (via the CLI) run at import time inside the printing process. Also:
   two small state bugs (salt write is not atomic; env swap is not re-entrant) and a no-budget score oracle.
2. **What failed, and why?** Nothing in the exam or the implementer's tests attacked the *candidate*; both checked output
   shape and leaky verifiers. A first draft of my CLI proof XPASSed for the wrong reason (the CLI exited 2 and printed
   nothing), so every proof now asserts the process succeeded before checking the leak, and was run with `--runxfail`.
3. **Which assumption was wrong?** "Run the service as a separate OS user and the store is private." That protects the
   store from the *agent user*, not from the *candidate*, which executes as the service user. Known limit "candidate
   sees the prompt, by design" understates it: the prompt is not the only thing reachable.
4. **What should the next agent know?** Fix RT-6..11 (small, local) first; RT-1..4 need an executor sandbox (a decision
   for the human: third OS user vs `sandbox-exec`/`bwrap`). Do not return executor-chosen numbers at full precision from
   AR4 (Sealed) either. Proofs are in `tests/arena/test_redteam_ar3.py`; remove each xfail marker when its fix lands.
