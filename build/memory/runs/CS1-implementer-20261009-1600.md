# CS1 · implementer run

1. **What did we learn?**
   - `executescript()` commits before it runs, so it cannot give one transaction per migration. `migrate()` splits each file
     with `sqlite3.complete_statement`, then runs each statement under `BEGIN IMMEDIATE` together with the `schema_version` insert.
   - `BEGIN IMMEDIATE`, plus re-reading the version inside the transaction, means concurrent migrators apply a version only once.
2. **What failed, and why?**
   - A concurrency test hung once, then failed about 1 time in 20 with `database is locked`. Cause: when several connections open a
     fresh file at once, `PRAGMA journal_mode = WAL` can return SQLITE_BUSY at once, without honouring the busy timeout.
     Fixed with a bounded retry in `_enable_wal`. The hang came from my own test, which waited on a barrier after a thread had died.
     Barriers in tests now have a timeout.
3. **Which assumption was wrong?**
   - That the `timeout=` argument to `sqlite3.connect` covers every lock wait. It does not cover the journal-mode switch.
   - That the spec type `JSON` is harmless. It gives NUMERIC affinity (see `open-problems/CS1.md`).
4. **What should the next agent know?**
   - Add a schema change as a new `migrations/000N_name.sql`. Never edit `0001`. Numbers must run 1..N with no gaps,
     or `migrate()` raises. The migration must not insert its own `schema_version` row, because `migrate()` writes it.
   - `migrate()` refuses a connection that already has an open transaction, and refuses a database newer than the code.
   - `open_db()` refuses any file named `tanishi.db`, `db.sqlite` or `finance.db`.
   - The schema declares no foreign keys, as the spec lists none. `PRAGMA foreign_keys` is on, so a later migration can add them.
   - Store only JSON objects or arrays in JSON columns. `.sql` files are not packaged yet (see `known-bugs/cs1-migrations-not-packaged.md`).
