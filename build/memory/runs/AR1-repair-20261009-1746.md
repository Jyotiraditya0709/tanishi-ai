# AR1 · repair round · 2026-10-09 17:46

Fixed RT-1 and RT-3 to RT-8, the env, process-group and duplicate-key items, and `.gitignore`. RT-2 is fixed in the code,
but its proof stays xfail. Contract: `decisions/0012-arena-attempt-contract.md` (was 0008).
Result: `310 passed, 2 xfailed`. The two xfails are proofs that conflict with the human's decisions:
`open-problems/AR1-repair-conflicts.md`.

1. **What did we learn?** Separating the executor from the verifier only helps if nothing secret ever enters the
   executor's process. Whatever is in its memory can be read (`gc`, frames), so the executor must be sent a `TaskBrief`
   built from scratch, not a `Task` with the verifier field removed. The return channel is untrusted too: the old runner
   unpickled what the child sent. With the executor in that child, a candidate could have run code in the runner. Children
   now send JSON only, and the runner writes every failure reason itself. Running children with `python -I` matters
   too: the temp `HOME` is also where Python looks for user-site `.pth` files, so without it a candidate could run code in
   the verifier process.
2. **What failed, and why?** Two red-team proofs cannot pass under the human's decisions. RT-2's proof expects score 0;
   the decision and the exam expect `ValueError`. RT-8's proof used RT-6 to kill the run, and RT-6 is fixed, so it now
   checks a complete run for an "incomplete" marker. I did not add a key just to satisfy it. My first `report_env` test
   probe overflowed the 500-char reason cap with long macOS temp paths, so it now reports booleans.
3. **Which assumption was wrong?** That multiprocessing spawn isolates the environment. It copies the caller's full
   environment at exec time. A process can read that starting environment back even after `os.environ.clear()`
   (`/proc/self/environ` on Linux, `KERN_PROCARGS2` on macOS; from the docs, not tried here).
   The minimal environment has to be passed to `exec`, so attempts are now `subprocess.Popen(env=...)` children. Also,
   one timeout covering both stages would let a slow candidate eat the verifier's time, so each stage gets `timeout_s`.
4. **What should the next agent know?**
   - Executors receive a `TaskBrief` (no `verifier`, no `setup`). An executor that calls a model must name its key in
     `run(..., env_passthrough=["NAME"])`. Nothing else is inherited.
   - `SeedResult.failure_kind` and `meta.failure_kind` tell candidate, verifier and infra failures apart. Filter out
     `infra` before blaming a candidate.
   - Rows appear only when `run()` returns. A long run that is interrupted leaves nothing, by design.
   - Open: daemons that double-fork escape (needs a sandbox); cost on failure is still 0; the verifier module is still
     importable by a candidate that guesses its name. AR3/AR4 must keep Frontier/Sealed verifiers out of reach.
   - Cost: each attempt is now two Python startups (not timed one by one). The whole suite (312 tests) runs in about 22 s.
