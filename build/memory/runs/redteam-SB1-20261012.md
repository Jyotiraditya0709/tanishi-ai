### 1 · Critical · the verifier stage runs the candidate's code, and it is not sandboxed

`tanishi/arena/practice/_common.py::_CodeProcess` starts `python -I _code_harness.py` with a bare `subprocess.Popen`
and the harness `exec`s the candidate's output string. That runs in AR1's verifier stage, which SB1 left unconfined
on purpose (decision 0025 §4, "the verifier reads only the output string"). For `run_python_tests` that premise is
false: the candidate's code is the output and it executes there, as the user, with no read or write limits. The
slugify/dedupe/fix_bug tasks, and every code task to come, hit this. Proof: the candidate's code reads a file
outside everything and writes it elsewhere; the verdict is still 1.0.

This is the card's goal ("code that Tanishi writes or changes runs only inside a sandbox") failing on the exact path
the loop uses for code. It also makes break 4 moot for those tasks.

Smallest fix: `_CodeProcess.__init__` starts the harness with `Sandbox(...).popen(argv, cwd=sb.workdir, stdin=PIPE,
stdout=PIPE, stderr=DEVNULL)`, `read_paths=[]`, the harness copied into scratch first (do not name
`tanishi/arena/practice/`, which holds task files), `network=False`, limits from `timeout_s`; kill via `sb.kill`;
`close()` closes the Sandbox. If no backend exists the verdict is a 0 as `infra`, like the executor stage.

### 2 · Critical · sysctl `KERN_PROCARGS2` is not gated by any profile rule

A candidate scans pids 2..99999 and reads argv + environment of each process of the same uid (408 seen on this
machine; the canary in an unrelated process was found). That includes the process that owns the Sandbox (Arena
runner, Frontier child, the loop) and the user's shell-exported keys, which every process started from that shell
inherits. The card names "a key" as something a candidate must never read.

I tried to close it with the profile and could not: `(deny sysctl*)`, `(deny process-info*)`,
`(deny sysctl-read (sysctl-name "kern.procargs2"))`, a full sysctl name allow-list, `(deny process-info-pidinfo)`:
all still return the data. Only `(deny sysctl-read)` stops it, and then Python does not start (`os.uname()`).
The kernel refuses it only across uids (pid 1 answers -1).

Smallest fix that works: run the candidate as a different uid (the card's own wording: "a separate process user"),
set up once with sudo (`sysadminctl -addUser tanishi-sandbox`, a sudoers rule for the launcher). Second best: on macOS
use Docker/a Linux VM when present (its pid namespace hides other processes) and have AR1 stop passing
`prefer_docker=False`; the sandbox-exec backend then stays as a fallback that the docs call "not key-safe". Whichever is
chosen, decision 0025 and the known-bugs file must stop saying that keys are unreachable on macOS.

### 3 · High · `(allow network* system-socket)` includes AF_UNIX

With `network=True` the candidate connected to a unix socket in a folder it has no read grant for and got data.
`docker.sock` is root on the host; an ssh-agent signs with the user's keys without any file being read. A task is
"granted network" for a package index, not for the host's IPC.
Fix (checked on this machine with the real profile: unix connect refused, TCP to 127.0.0.1 still works):
replace that line with
`(allow system-socket)` `(allow network-outbound (remote ip))` `(allow network-bind (local ip))`.
Not checked: DNS under that profile (may need `mach-lookup com.apple.dnssd.service` / `com.apple.SystemConfiguration.DNSConfiguration`).
Linux: Landlock ABI < 6 does not restrict connect() to pathname unix sockets either; I did not test it. If true,
`deny_net` needs a seccomp rule on `socket(AF_UNIX)`/`connect`, or the grant should be Docker only.

### 4 · High · a read path is a whole tree

`Sandbox.read_paths` entries are granted recursively and only five names are carved out. AR1 passes every
`sys.path` entry, which includes the repo root (or the cwd when run with `-m`, or `''`). `data/db.sqlite` (the legacy
conversation db, CLAUDE.md) and any other `*.db`, `.pem`, `.netrc`, `.aws/` under it are readable.
Fix: AR1's `_import_paths()` grants the `tanishi/` package dir and site-packages, never the repo root, never `''`/the
cwd; and `darwin_profile` adds `*.db`, `*.sqlite*`, `*.pem`, `*.key`, `id_*`, `.netrc`, `.aws`, `.gnupg` to the
deny regex (Landlock: same names in `is_guarded_name`).

### 5 · High · the worktree copy

`_not_copied` leaves out only guarded names. With `worktree=` the candidate gets `data/db.sqlite`, any `*.db`,
and the checkout's `.git` (a directory in a main checkout: every object ever committed, including a file that
was committed before it became a protected path). The copy lands in scratch, which the profile allows in full.
Fix: skip `.git`, names matching the same secret patterns as break 4, and anything the repo's own `.gitignore` ignores
(`git ls-files` is the allow-list; copy only tracked files).

### 6 · Medium · rollback is not guaranteed

`chflags uchg` is allowed inside scratch. `_force_rmtree` swallows the resulting EPERM, then `_fill()`'s
`mkdir` raises `FileExistsError` and the candidate's file is still there: a rollback that raises mid-way, scratch
left half-wiped, and `close()` leaves the folder on disk (a disk-fill that persists).
Fix: in `_force_rmtree`'s handler call `os.chflags(p, 0)` (and the parent) before retrying; make `rollback()` create a
fresh scratch with `mkdtemp` and delete the old one best-effort, so a stuck file cannot block the next run; make
`close()` report (log, raise after cleanup) when scratch is still there.

### 7, 8 · Medium · process count and disk

Both were listed in known-bugs as unlimited; the tests pin what that means: 200 forked children are all allowed
(a real bomb is bounded only by the user's `kern.maxprocperuid`, which the user's whole session shares), and 200 MB
is written in 0.3 s. Fixes: `_Watch._loop` already lists the tree every 0.1 s; add `max_processes` (default 64) and
`max_disk_mb` (sum of scratch file sizes, default 256) there, kill with `limit="processes"`/`"disk"`; set
`RLIMIT_FSIZE` in `_launch.py` as a cheap per-file cap.

### 9 · Low · case-sensitive copy filter

The profile is fine (the kernel gives it the canonical path; `test_rt2…not_bypassed…` guards that), but
`is_guarded_name` is used by `_not_copied`, and a checkout folder spelled `Vault`/`.ENV` is copied. Fix: compare
`name.lower()`.

## What I tried that held

- Case variants of `vault`, `builder_vault`, `traces`, `.ssh`, `.env` through a read path: refused (guard test).
- `link(2)`, `clonefile(2)` and `rename(2)` from a file inside `vault/` into scratch: all refused, source intact (guard).
- A 1200-level directory made by mkdir+chdir: `close()` removed it (guard). (Making it takes seconds of CPU:
  the sandbox's CPU limit killed a 3000-level attempt at 10 s.)
- Unix-socket connect with `network=False`: refused.
- Reading a `.env`/`vault` copy is also impossible through the plain names; exam canaries are covered by the SB1 exam.

## Review notes, not tested

- Linux: the guard list is applied one level deep (known); `_LINUX_READ` grants all of `/etc`; the launcher's own
  `/proc/<pid>` is granted `ro` for child discovery. No finding without a host to run it on.
- Docker: `prefer_docker=True` is the default but AR1 sets it False, so the AR1/Frontier path never uses Docker even
  on a machine that has it. On Docker Desktop for Mac a bind-mounted read path is on a case-insensitive host
  filesystem, so the `--tmpfs` over `vault/` would be bypassed by `VAULT/`; I could not run it.
- `popen(stdin=None/stdout=None)` inherits the parent's descriptors; only `run()` sets them. Callers of `popen`
  that forget are one `print` from sending the parent's stdin to a candidate.
- `_kill_run` calls `os.killpg`/`_kill_members` with a pid that may have been reaped; a recycled pid could be hit.
  Needs a pid wrap during the window: not reproduced, theoretically possible.
- CPU limit is per process (RLIMIT_CPU): a tree of N processes burns N times the budget until the wall limit.
- The verifier stage still reads the candidate's files in its cwd (a symlink named like the file the verifier opens);
  already in known-bugs, now with break 1 in the same stage.
- Rollback hash check: guarded folders were not touched by any attack above; scratch is the only thing that changed.

## After-task questions

1. **What did we learn?** Default-deny file rules are not enough on macOS: process introspection (`KERN_PROCARGS2`) and
   unix sockets are separate channels, and the profile language has no verb for the first. The same-uid problem
   needs a different uid or a different kernel (container/VM).
2. **What failed, and why?** Four profile-only attempts to hide other processes' environments (see break 2): the
   kernel does not route that call through the sandbox's sysctl or process-info filters.
3. **Which assumption was wrong?** Decision 0025 §4: "the verifier only reads the output string". `run_python_tests`
   executes the output. Also the implicit one that `network=True` means "internet": the profile grants all local IPC.
4. **What should the next agent know?** Fix 1 and 2 before M1 closes the loop; fix 3-5 are one-line-ish. The xfail
   marks are strict: removing the break flips the test, then delete the mark. Do not re-derive break 2 from the profile;
   the table of variants I tried is above.
