## Design points (no failing test: they need a decision, not a patch)

- **The ledger cannot prove a prediction came first.** `predict()` and `resolve()` are public, and any caller can predict at
  confidence 1.0 and resolve it a microsecond later with the answer it likes, for a Brier of 0. Nothing ties `actual` to
  a `tool_result` event or `predict` to a moment before the action. Fine while the only writer is `execute()`; before the
  Self Model or the Arena trusts `calibration()` as a score, the Arena must read calibration only from rows linked to a
  `call_id` in the event log (add `call_id` to the `prediction` payload), or compute it from events, not from the table.
- **Four events per tool call, not two** (`prediction`, `tool_call`, `tool_result`, `prediction_resolved`). The log doubles
  in size per call. The prediction rows already hold the same data.
- Already in `known-bugs/cs5-prediction-ledger-limits.md`: no SQL-level resolve-once, row and event not one transaction,
  three db opens per call, sync db work in async code, forecast ignores the input.

## Held (tried, no break)

Secrets in `about`, `expected`, `actual` (keys and values) never reach the row or the events (H1). Cyclic and 5,000-deep
`expected` are handled (H2). Eight threads predicting and resolving at once: counts right, each resolved once, hash chain
verifies (H3, and the existing concurrent-resolve test). Latency NaN from `execute()` cannot happen: the registry computes
`execution_time_ms` itself and a handler returning a `ToolResult` is wrapped as output. Wrong types and bool confidence
are refused with nothing written (the exam covers it).
