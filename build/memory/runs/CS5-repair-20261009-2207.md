## Four questions

1. **What did we learn?** "Resolve on every path" mixed two questions: is the ledger complete, and what does the
   forecaster believe. The forecaster must only learn from outcomes of the tool; completeness is the event log's job.
   Splitting the gate from the run made "did the handler run" a structural fact instead of a flag.
2. **What failed, and why?** Migration 0003 failed three CS4 builder tests that assert the schema version is exactly 2.
   Any new migration from any node would. My own first R4 test had the wrong expected value (I counted a row the
   forecaster never reads); the code was right.
3. **Which assumption was wrong?** That the card's R6 ValueError and the R6 red-team test agree: the test asserts a
   list for NaN/inf/1e12. The test won. Also that a new migration is additive: tests that pin a global (the schema
   version, the whole event log) turn every later node's growth into a break.
4. **What should the next agent know?** Never assert `migrate(c) == N` or compare the whole event log to a list;
   assert the property you own. Do not score Arena candidates from `calibration()` (`open-problems/CS5.md`). An
   unresolved tool prediction now means "never reached the tool" or "forgotten"; a `void` state would split them.
