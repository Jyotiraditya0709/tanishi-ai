# AR1 · tester · 2026-10-09 17:30

1. **What did we learn?** The AR1 card is enough to test isolation, row accounting and failure-scores-zero, because a verifier
   can observe `TANISHI_HOME` and `TANISHI_CORE_STATE_DB` from inside the run. Probe verifiers that log what they saw
   let the exam check "fresh home per task and seed" without knowing how the runner works.
2. **What failed, and why?** Nothing ran against an implementation (none exists yet; collection fails on
   `tanishi.arena`, which is the intended red state). I first wrote tests for helper names the spec does not give
   (`verifiers.resolve`) and removed them; a tester should not invent API.
3. **Which assumption was wrong?** That the card fully defines the interface. It does not say how a candidate produces output,
   what a verifier receives, what `setup` is, or what `RunResult` holds. See `open-problems/AR1-exam-assumptions.md` (A1 to A6).
4. **What should the next agent know?** The implementer must read the A-list before building; `load_task` and the error types
   are assumptions. "Crashed or empty run scores 0" is only covered for verifier-side failures until an executor interface
   exists. Tests live in `tests/arena/` (helpers in `arena_helpers.py`, probes in `conftest.py`). Do not edit them to fit; file a conflict note instead.
