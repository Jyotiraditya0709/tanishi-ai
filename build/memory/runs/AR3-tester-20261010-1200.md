# AR3 · tester · 2026-10-10

Exam: `tests/arena/test_frontier.py` (28 tests, one hypothesis property test). Assumptions: `open-problems/AR3-exam-assumptions.md`.

1. **What did we learn?** The boundary has more doors than the return value. AR1's `run()` writes `task_id` and the
   verifier's `reason` into `experiments` in the Core State, which the agent can read. A thin wrapper around `run()` leaks
   the expected answer there even when the API returns only `{task_id_hash, score, cost}`. I proved this with a throwaway
   reference stub (deleted, not committed): 27 of 28 tests passed, the failing one was the Core State scan.
2. **What failed, and why?** Nothing in the exam is expected to pass today: with no `frontier_service.py`, all 28 tests
   fail on import, so none passes against `pass`/an empty module. The stub run was only to prove the tests can be satisfied.
3. **Which assumption was wrong?** I assumed the spec would at least name an entry point. It names only a file. API names
   (A1) and store layout (A2) are mine; a conflict file from the implementer is expected and fine.
4. **What should the next agent know?** The "OS user cannot read" line is only half testable from inside the agent's
   user: the exam checks mode bits and repo location, not ownership (A7). The human must verify ownership at deploy time.
   The implementer must keep reasons and raw task ids out of the caller's Core State (A5), and should consider salting the
   hash (A4). Red-team should try: candidate that reads the store by path, task file symlinks out of the store, a store
   directory swapped after construction (TOCTOU), and reason/ID leakage via `duration_s`-style side channels.
